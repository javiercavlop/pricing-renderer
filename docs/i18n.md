# Internationalization

Source messages, API names, and documentation are English. Runtime defaults are
deterministic `en-US`; `es-ES` is included as a complete extension example.
The integrating project selects the initial locale through configuration. The
library does not add a language selector to the pricing UI; any selector in the
showcase belongs to the demo host.

## Select a locale

Configure the library before creating renderer instances:

```ts
import { configurePricingRenderer } from 'pricing-renderer';

configurePricingRenderer({
  locale: 'es-ES',
  pricingPath: '/precios',
});
```

If configuration is omitted, the locale is always deterministic English
(`en-US`). (`pricingPath`, default `/pricing`, is deprecated metadata kept for
compatibility: the host router owns the route and nothing in the renderer reads
it.) Global
configuration supplies defaults for subsequently created instances; per-instance
properties take precedence. In an SSR server shared by multiple tenants, prefer
per-instance props instead of mutating process-wide configuration per request.

The same settings can be overridden for one instance:

```html
<pricing-renderer locale="es-ES" pricing-path="/precios"></pricing-renderer>
```

```tsx
<PricingRenderer pricing={pricing} locale="es-ES" pricingPath="/precios" />
```

Library-owned currency and dates use `Intl.NumberFormat` and
`Intl.DateTimeFormat`. YAML-owned names, descriptions, labels, units, and CTA
copy are not translated automatically; provide localized pricing content or
override presentation values in the host.

## Unit labels

A unit next to a number is pluralized only by the built-in rules: an English
naive plural, with other units left as written. To control the text, set
`presentation.unitLabels` (see [Unit labels](configuration.md#unit-labels)):

```ts
renderer.presentation = {
  unitLabels: {
    es: { credit: { one: 'crédito', other: 'créditos' } },
  },
};
```

For the UI locale, the label is looked up in this order: the exact locale tag
(`es-MX`), the base language (`es`), the `*` key, and then the built-in rules.
The first entry found wins, even for compound or uppercase units such as
`user/month` or `GB`, and for a count of 1. `one` is used when the plural
category of the locale for the count is `one`, otherwise `other`. Entries that
are not an object, or whose `one` or `other` is missing, not a string or blank,
are ignored without an error.

Layers merge per locale key first, then this lookup order applies to the merged
map, so an exact-locale entry from a lower layer wins over a `*` or
base-language entry from a higher layer. Locale keys ignore case and treat `_`
as `-`.

## Override a message for one renderer

```ts
renderer.messages = {
  'pricing.choosePlan': 'Select {plan} for this workspace',
};
```

Overrides merge on top of the selected catalog.

## Register a reusable catalog

```ts
import { enUS, registerMessageCatalog } from 'pricing-renderer';

export const ptBR = {
  ...enUS,
  'pricing.plans': 'Planos',
  'pricing.addOns': 'Complementos',
  'pricing.choosePlan': 'Escolher {plan}',
};

registerMessageCatalog('pt-BR', ptBR);
```

The registry uses exact locale tags first, then a registered catalog from the
same language family, then `en-US`. `getRegisteredLocales()` is useful for
building a language picker.

## Catalog contribution checklist

- Start from all keys in `enUS`.
- Preserve interpolation names such as `{plan}`, `{count}`, or `{percent}`.
- Keep labels concise enough for 320 px and 400% zoom.
- Do not manually concatenate plural-sensitive sentences.
- Test dates, currency placement, decimal separators, and negative values.
- Test long words, RTL where relevant, and screen-reader names.
- Add unit tests for registry fallback and browser coverage for the catalog.

## RTL

Set direction on the host document or a containing element:

```html
<div dir="rtl">
  <pricing-renderer locale="ar"></pricing-renderer>
</div>
```

The supplied CSS uses logical properties. A new RTL catalog must still be
visually and keyboard-tested; text direction is a host/content decision.

## Message keys

`enUS` is the canonical, typed-at-runtime catalog. Import it to inspect or extend
the current key set:

```ts
import { enUS } from 'pricing-renderer';
```

The price breakdown disclosure in the summary uses three keys:

- `pricing.breakdownToggle`: `en-US` "How is this calculated?", `es-ES`
  "¿Cómo se calcula?".
- `pricing.breakdownTitle`: `en-US` "Price breakdown", `es-ES` "Desglose del
  precio".
- `pricing.breakdownFormula`: `{unitPrice} × {quantity} × {multiplier} = {amount}`
  in both catalogs.

`breakdownToggle` is the accessible name of the button and `breakdownTitle` the
name of the panel. `unitPrice` and `amount` are formatted as currency and
`quantity` and `multiplier` with `Intl.NumberFormat` for the locale.

The current plan, the plan CTAs and the summary action use seven keys. They apply
only when the host sets `currentSelection` or `pendingActionId`:

- `pricing.currentPlanBadge`: `en-US` "Your plan", `es-ES` "Tu plan".
- `pricing.currentPlanCta`: `en-US` "Current plan", `es-ES` "Plan actual".
- `pricing.upgradeTo`: `en-US` "Upgrade to {plan}", `es-ES` "Mejorar a {plan}".
- `pricing.downgradeTo`: `en-US` "Downgrade to {plan}", `es-ES` "Bajar a {plan}".
- `pricing.currentAddOn`: `en-US` "Current", `es-ES` "Actual".
- `pricing.reviewChangeCta`: `en-US` "Review change ({total})", `es-ES` "Revisar
  cambio ({total})".
- `pricing.pending`: `en-US` "Processing…", `es-ES` "Procesando…".

`{plan}` is the plan name and `{total}` the formatted subtotal. A plan whose price
is a label or needs a quote uses the existing `pricing.contactSales` instead of
`pricing.upgradeTo` or `pricing.downgradeTo`, and so does the summary action when
the selection needs a quote. To word one plan's CTA differently, set
`labels` on its entry of `presentation.ctas` (see
[Configuration](./configuration.md)); CTA copy from the pricing is not translated
automatically.

### Error and loading keys

While the element loads, the hidden heading and the status text use
`pricing.loading` (`en-US` "Loading pricing…", `es-ES` "Cargando precios…"),
unless the host sets `loadingLabel`, which wins. `messages` overrides apply.

The error state shows `pricing.error` as its heading, `pricing.retry` on the retry
button (only when `src` is set) and one sentence by the category of the first
diagnostic with severity `error`. Five keys were added for it:

- `pricing.errorSource`: `en-US` "The pricing source could not be loaded.",
  `es-ES` "No se pudo cargar el origen del pricing." For codes that start with
  `PR_SOURCE_`, and `PR_FETCH_UNAVAILABLE`.
- `pricing.errorFormat`: `en-US` "The pricing file is not a valid Pricing2Yaml
  document.", `es-ES` "El archivo de pricing no es un documento Pricing2Yaml
  válido." For codes that start with `PR_YAML_`, and `PR_INPUT_INVALID`.
- `pricing.errorVersion`: `en-US` "This Pricing2Yaml version is not supported.",
  `es-ES` "Esta versión de Pricing2Yaml no es compatible." For codes that start
  with `PR_VERSION_`.
- `pricing.errorGeneric`: `en-US` "The pricing data has errors.", `es-ES` "Los
  datos del pricing tienen errores." For any other code, or when no diagnostic has
  severity `error`.
- `pricing.errorDetails`: `en-US` "Technical details", `es-ES` "Detalles
  técnicos". The summary of the closed `details` element
  (`data-pr-part="diagnostics"`) that lists each diagnostic with its code, message
  and path.

The visible sentence has no diagnostic code. The codes stay in that `details`
element and in the `pricing-diagnostic` event (see [Events](./events.md)). A
catalog that you register should define the five keys, as the other keys of
`enUS`.

New first-party messages should be added to both built-in catalogs in the same
change. Removing or changing the meaning of a public key follows SemVer.
